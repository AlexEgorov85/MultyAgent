# Analytics Agent

## Purpose

Отвечает на количественные вопросы аудитора: строит проверяемый QueryPlan,
выбирает способ выполнения (шаблон по контракту или SQL), проверяет его,
выполняет и возвращает ответ с числовыми доказательствами.

## Requirements

### Requirement: Приём ACL-запроса

Система SHALL начинать работу Analytics-подагента только после валидации входящего ACL-сообщения.

#### Scenario: Корректный запрос

- **WHEN** получен `request` с вопросом, `auditor_id` и `conversation_id`
- **THEN** подграф разбирает запрос и строит план выполнения

#### Scenario: Некорректный ACL

- **WHEN** отсутствует обязательное поле или неверный `performative`
- **THEN** подграф возвращает `refuse` или `failure`
- **AND** не вызывает LLM и tools

### Requirement: Планирование стратегии

Система SHALL возвращать структурированный `SQLPlan` со стратегией `script` или `generated`.

#### Scenario: Подходящий готовый шаблон

- **WHEN** LLM выбрала `template_key` из `script_templates` и проверенный
  `QueryPlan` полностью покрывается контрактом шаблона
- **THEN** код выбирает стратегию `script`
- **AND** формирует параметры шаблона из плана
- **AND** проверяет обязательные параметры до запуска
- **AND** неподходящий шаблон отклоняется

#### Scenario: Нужен сгенерированный SQL

- **WHEN** ни один контракт шаблона не покрывает план
- **THEN** код выбирает стратегию `generated`
- **AND** SQL собирает компилятор по `QueryPlan`

### Requirement: Query IR и semantic layer

Система SHALL сначала пытаться построить структурированный `QueryPlan`
по каталогу метрик и измерений и SHALL генерировать SQL детерминированным
компилятором для поддержанных метрик.

#### Scenario: Поддержанная метрика

- **WHEN** вопрос сводится к метрике каталога
- **THEN** LLM возвращает `QueryPlan(metric, dimensions, filters)`
- **AND** SQL собирает компилятор, а не LLM
- **AND** в метриках ответа фиксируется `plan_source = query_ir`

#### Scenario: Неподдержанный запрос

- **WHEN** метрика, разрез или значение не входят в каталог
- **THEN** Analytics откатывается на свободный `SQLPlan`
- **AND** fallback проходит тот же SQL-guard

#### Scenario: Выбор шаблона по контракту

- **WHEN** план описывает сводку по статусам, топ видов отклонений,
  динамику по темам, просроченные пункты или пункты без скриптов
- **THEN** LLM выбирает `template_key` из списка шаблонов
- **AND** код проверяет контракт: метрику, разрезы, фильтры и период
- **AND** шаблон запускается, только если контракт полностью покрывает план
- **AND** неподходящий шаблон отклоняется, и SQL собирается из Query IR

#### Scenario: Шаблон не покрывает вопрос

- **WHEN** контракт шаблона не покрывает план или параметры недопустимы
- **THEN** шаблон отклоняется
- **AND** SQL собирается из `QueryPlan`
- **AND** вопрос не подменяется другим разрезом или фильтром

#### Scenario: Неполный QueryPlan

- **WHEN** LLM вернула верный смысл в `reason`, но пустые
  `dimensions`/`filters`
- **THEN** `complete_query_plan` дополняет план доменными сигналами
  semantic layer (карман, последний год, закрытая проверка, тема, AUD-код)
- **AND** существующие условия плана не перезаписываются
- **AND** при нескольких значениях одного поля выбирается разрез, а не
  несколько одновременных фильтров

#### Scenario: Разрез по карманам

- **WHEN** вопрос просит «по каждому карману»
- **THEN** план использует измерение `pocket`, а не `status`
- **AND** шаблон по статусам отклоняется, если он не содержит разрез по карманам
- **AND** SQL собирается из `pocket` + остальных условий вопроса

### Requirement: Слоты диалога

Система SHALL переносить год и код проверки между репликами детерминированно,
а семантические сущности (тема, тип находки, риск, статус) SHALL восстанавливать
LLM-резолвер по смыслу и контексту.

#### Scenario: Смена года после уточнения типа

- **WHEN** пользователь уточнил «проблемы», затем спросил «А за 2025 год?»
- **THEN** LLM-резолвер переформулирует вопрос с типом находки и годом
- **AND** `resolved_query` содержит год и тип находки
- **AND** код не угадывает тип находки по отдельным словам

#### Scenario: Омонимия темы

- **WHEN** вопрос содержит «картина отклонений» или «карта проверок»
- **THEN** система не подставляет тему «карты»
- **AND** тему определяет LLM по смыслу, а код проверяет её по списку допустимых значений

### Requirement: Режим Analytics выбирает LLM

Система SHALL выбирать режим Analytics (`sql`, `drilldown`, `multi_tool`)
по смыслу вопроса на уровне router и SHALL валидировать значение по enum.

#### Scenario: Пункты конкретной проверки

- **WHEN** router вернул `analytics_mode = drilldown` и в вопросе есть AUD-код
- **THEN** Analytics выполняет drill-down по пунктам проверки
- **AND** не выбирает режим по отдельным словам

#### Scenario: Несколько инструментов

- **WHEN** router вернул `analytics_mode = multi_tool`
- **THEN** Analytics одним вызовом LLM планирует несколько инструментов
- **AND** лог содержит оба вызова

#### Scenario: Неизвестный режим

- **WHEN** в ACL пришёл неизвестный `analytics_mode`
- **THEN** Analytics использует `sql`
- **AND** не падает

### Requirement: Генерация SQL по схеме

Система SHALL строить SQL только по доступной схеме `audit` и с учётом русских значений перечислений.

#### Scenario: Фильтр по статусу

- **WHEN** вопрос требует завершённые проверки
- **THEN** SQL использует `status = 'завершена'`
- **AND** не подставляет английские значения

#### Scenario: Закрытая проверка

- **WHEN** вопрос говорит о закрытых проверках
- **THEN** фильтр выбирается по метрике проверок (`status = 'завершена'`)
- **AND** слово «закрыт» само по себе не определяет статус без контекста метрики

#### Scenario: Закрытый пункт

- **WHEN** вопрос говорит о закрытых пунктах
- **THEN** фильтр выбирается по метрике пунктов (`status = 'закрыт'`)
- **AND** не подставляется статус проверки `завершена`

#### Scenario: Последний год

- **WHEN** вопрос просит «за последний год»
- **THEN** план использует `year = "last"`
- **AND** компилятор подставляет максимальный год данных, а не
  захардкоженный год
- **AND** шаблон с фиксированным годом по умолчанию не считается
  покрывающим этот период

#### Scenario: Неоднозначный вопрос

- **WHEN** вопрос не содержит периода или кармана, а результат зависит от них
- **THEN** агент либо задаёт уточнение, либо явно фиксирует допущение в ответе

### Requirement: Визуализация данных

Система SHALL строить диаграмму по данным предыдущего аналитического
ответа, когда пользователь просит визуализацию, и SHALL не подменять её
повторным SQL-ответом.

#### Scenario: Диаграмма по предыдущим данным

- **WHEN** пользователь просит «построй диаграмму на основании этих данных»
- **THEN** запрос не переписывается в новый SQL-вопрос
- **AND** Analytics использует строки и колонки предыдущего ответа
- **AND** возвращает `answer` и `chart` в ACL `inform`
- **AND** UI отображает диаграмму, а не повторную таблицу

#### Scenario: Выбор типа диаграммы

- **WHEN** данные и запрос переданы планировщику визуализации
- **THEN** LLM выбирает `bar`, `line` или `pie` и подписи по смыслу
- **AND** каждая точка диаграммы проверяется по исходным строкам
- **AND** выдуманные точки отбрасываются
- **AND** при недоступности LLM используется детерминированный fallback

#### Scenario: Нет предыдущих данных

- **WHEN** диаграмма запрошена, но предыдущего аналитического результата нет
- **THEN** агент объясняет, что сначала нужен числовой вопрос
- **AND** не выполняет произвольный SQL и не показывает пустую диаграмму

### Requirement: Проверка перед выполнением

Система SHALL проверять сгенерированный SQL через SQL-guard и SHALL не выполнять запрос, не прошедший проверку.

#### Scenario: Опасный SQL

- **WHEN** модель сгенерировала `DELETE` или обращение к чужой схеме
- **THEN** запрос не выполняется
- **AND** агент возвращает отказ или пытается построить безопасный вариант

#### Scenario: Ошибка выполнения

- **WHEN** PostgreSQL вернул синтаксическую или семантическую ошибку
- **THEN** агент исправляет SQL по тексту ошибки
- **AND** делает не более двух попыток исправления

### Requirement: Ответ с доказательствами

Система SHALL возвращать ответ, строки результата, выполненный SQL и evidence.

#### Scenario: Успешный аналитический ответ

- **WHEN** запрос выполнен и вернул строки
- **THEN** ответ содержит числа и единицы измерения
- **AND** приложены SQL и `query_id`
- **AND** evidence ссылается на результат SQL

#### Scenario: Пустой результат

- **WHEN** запрос корректен, но вернул 0 строк
- **THEN** агент сообщает, что по заданным условиям ничего не найдено
- **AND** показывает условия и не выдумывает данные

### Requirement: Фильтрация и детализация

Система SHALL поддерживать drill-down по карману, проверке, акту и пунктам.

#### Scenario: Пункты конкретной проверки

- **WHEN** вопрос содержит код проверки, например `AUD-2026-MORTGAGE-03`
- **THEN** агент возвращает пункты этой проверки с номерами, риском и сроками
- **AND** evidence содержит `item_id`

### Requirement: Несколько инструментов в одном вызове LLM

Система SHALL поддерживать сценарий, в котором один вызов LLM запрашивает два и более инструмента.

#### Scenario: Комбинированный запрос

- **WHEN** пользователь просит найти отклонения по проверке и похожие формулировки в других актах
- **THEN** LLM в одном ответе вызывает `get_act_items` и `search_acts`
- **AND** лог содержит оба вызова с аргументами и результатами

### Requirement: Ограничение цикла инструментов

Система SHALL ограничивать число итераций tool-caller и SHALL завершать работу отказом при исчерпании лимита.

#### Scenario: Инструменты не дают результата

- **WHEN** достигнут `MAX_AGENT_ITERATIONS`
- **THEN** агент прекращает вызовы
- **AND** возвращает частичный ответ с указанием, что данных недостаточно
