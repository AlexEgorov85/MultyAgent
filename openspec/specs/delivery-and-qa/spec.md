# Delivery and QA

## Purpose

Гарантирует, что проект можно проверить с нуля: репозиторий чистый, README достаточен, тесты зелёные, скринкаст доступен, а спецификации соответствуют реализации.

## Requirements

### Requirement: Структура репозитория

Система SHALL находиться в корне выданного репозитория и SHALL использовать ветку `main`.

#### Scenario: Проверка расположения

- **WHEN** проверяющий открывает репозиторий
- **THEN** README и исходный код находятся в корне
- **AND** нет вложенной папки проекта

#### Scenario: Проверка ветки

- **WHEN** выполняется `git branch`
- **THEN** активна ветка `main`
- **AND** сдача не зависит от других веток

### Requirement: README как точка входа

README SHALL содержать разделы: о проекте, скринкаст, запуск, архитектура, примеры, технологии.

#### Scenario: Запуск по README

- **WHEN** новый пользователь выполняет инструкции по порядку
- **THEN** он устанавливает зависимости, готовит данные, запускает backend и интерфейс
- **AND** может выполнить тесты и оценку

#### Scenario: Описание ограничений

- **WHEN** пользователь читает README
- **THEN** он видит ограничения краткосрочной памяти, синтетических данных и безопасности
- **AND** не получает ложных обещаний о production-готовности

### Requirement: Чистый клон

Система SHALL запускаться из чистого клона без ручных исправлений.

#### Scenario: Проверка с нуля

- **WHEN** проект клонирован в пустой каталог
- **THEN** генерация seed, миграции, построение индекса, тесты и запуск проходят по README
- **AND** не требуются файлы, отсутствующие в репозитории

### Requirement: Отсутствие секретов и тяжёлых артефактов

Репозиторий SHALL NOT содержать `.env`, ключи, кластер PostgreSQL, сгенерированные CSV, векторные индексы, видео и архивы.

#### Scenario: Проверка перед push

- **WHEN** выполняется финальная проверка
- **THEN** `.gitignore` исключает `.venv`, `data/pg/`, `data/seed/`, `.env`
- **AND** `git status` не показывает секретов и больших файлов

### Requirement: Тесты

Система SHALL иметь автоматические тесты ключевых контрактов.

#### Scenario: Обязательный набор тестов

- **WHEN** выполняется `pytest -q`
- **THEN** проходят тесты ACL, SQL-guard, tools, памяти, RAG, маршрутизации и investigation
- **AND** падение любого из них блокирует сдачу

### Requirement: Проверки интерфейса

Система SHALL иметь воспроизводимые проверки frontend, не сводящиеся к ручному запуску.

#### Scenario: Линтер и сборка

- **WHEN** выполняются `npm --prefix ui run lint` и `npm --prefix ui run build`
- **THEN** обе команды завершаются с кодом 0
- **AND** сборка не выдаёт предупреждений о трассировке лишних файлов или корне Turbopack

### Requirement: Скринкаст

Система SHALL иметь скринкаст длительностью не более 10 минут с демонстрацией ключевых сценариев.

#### Scenario: Проверка видео

- **WHEN** ссылка открывается в режиме инкогнито
- **THEN** видео доступно без запроса доступа
- **AND** показаны аналитика, поиск, отчёт, расследование, память и guardrail

### Requirement: Синхронизация спецификаций и кода

Система SHALL поддерживать OpenSpec-спецификации в актуальном состоянии и SHALL проходить их валидацию.

#### Scenario: Проверка спецификаций

- **WHEN** выполняется `openspec validate --specs --strict`
- **THEN** все спецификации валидны
- **AND** реализованное поведение не противоречит требованиям

#### Scenario: Изменение поведения

- **WHEN** требование меняется в ходе разработки
- **THEN** соответствующий `spec.md` обновляется в том же изменении
- **AND** расхождение не остаётся только в коде или в чате
