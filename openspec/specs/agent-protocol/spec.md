# Agent Protocol

## Purpose

Задаёт единый FIPA-ACL-конверт для всех межагентных вызовов, чтобы взаимодействие было явным, проверяемым и воспроизводимым в логах.

## Requirements

### Requirement: Единый ACL-конверт

Система SHALL использовать модель `ACLMessage` для любого взаимодействия между Router, Coordinator, Analytics, Retrieval, Report, Inspector и Guardrail.

#### Scenario: Вызов подагента

- **WHEN** основной граф передаёт работу Analytics
- **THEN** создаётся `ACLMessage` с `performative = request`
- **AND** сообщение валидируется до вызова

#### Scenario: Прямой вызов запрещён

- **WHEN** код пытается вызвать функцию подагента без ACL-конверта
- **THEN** тест архитектуры фиксирует нарушение
- **AND** вызов не считается допустимым

### Requirement: Обязательные поля сообщения

Система SHALL требовать наличия `performative`, `sender`, `receiver`, `content`, `conversation_id` и `reply_with`.

#### Scenario: Полное сообщение

- **WHEN** сообщение содержит все обязательные поля
- **THEN** валидация проходит
- **AND** сообщение может быть обработано адресатом

#### Scenario: Пропущено поле

- **WHEN** отсутствует `conversation_id` или `reply_with`
- **THEN** валидация завершается ошибкой
- **AND** сообщение не передаётся агенту

### Requirement: Допустимые перформативы

Система SHALL поддерживать `request`, `inform`, `refuse`, `failure`, `propose` и `agree`.

#### Scenario: Успешный ответ

- **WHEN** агент вернул результат
- **THEN** используется `inform`
- **AND** `content` содержит результат и evidence

#### Scenario: Отказ

- **WHEN** запрос нарушает правила безопасности
- **THEN** используется `refuse`
- **AND** `content.reason` объясняет причину на русском языке

#### Scenario: Техническая ошибка

- **WHEN** агент не смог выполнить работу из-за сбоя
- **THEN** используется `failure`
- **AND** указывается, что именно не удалось

### Requirement: Корреляция диалога

Система SHALL связывать ответ с запросом через `conversation_id`, `reply_with` и `in_reply_to`.

#### Scenario: Ответ на запрос

- **WHEN** агент отвечает на сообщение с `reply_with = msg-0001`
- **THEN** ответ содержит `in_reply_to = msg-0001`
- **AND** сохраняет тот же `conversation_id`

#### Scenario: Несколько раундов

- **WHEN** Coordinator делает второй раунд
- **THEN** новый запрос содержит новый `reply_with`
- **AND** `conversation_id` остаётся прежним

### Requirement: Валидация и запрет неоднозначности

Система SHALL отклонять сообщения с неизвестным `performative`, пустым `content` или неверным типом полей.

#### Scenario: Неизвестный перформатив

- **WHEN** `performative = "execute"`
- **THEN** Pydantic-валидация отклоняет сообщение
- **AND** ошибка фиксируется в логе

### Requirement: Журналирование обмена

Система SHALL сохранять все ACL-сообщения в структурированном логе запуска.

#### Scenario: Разбор инцидента

- **WHEN** пользователь или разработчик открывает лог
- **THEN** видна последовательность сообщений с отправителем, получателем, временем и корреляцией
- **AND** по `conversation_id` можно восстановить весь диалог

### Requirement: Язык и онтология

Система SHALL использовать `language = "ru"` и единую онтологию проекта.

#### Scenario: Сообщение по умолчанию

- **WHEN** агент создаёт сообщение без явного языка
- **THEN** устанавливается `language = "ru"`
- **AND** `ontology` соответствует домену аудита
