# Бенчмарк: простые, сложные и цепочечные вопросы

Бенчмарк сделан по логике занятия 7: фиксированный набор задач с заранее
известными ответами, прогон на одинаковых данных, затем `SR/ER`, точность
маршрута, tool-call accuracy и latency. В отличие от `data/test_cases.jsonl`,
здесь отдельно выделены **три уровня сложности** и **диалоговые цепочки**.

## Зачем нужен отдельный набор

`data/test_cases.jsonl` проверяет обязательные сценарии по одному вопросу.
Новый набор отвечает на три вопроса:

1. **Простые вопросы** — справляется ли система с одним фактом и одним
   инструментом.
2. **Сложные вопросы** — выдерживает ли multi-tool, отчёт, расследование и
   многомерную аналитику.
3. **Цепочки** — переносит ли система год, тему и код проверки из предыдущих
   реплик; не теряет ли контекст после перезапуска нити.

## Уровни

### Simple — один факт

Проверяется маршрут, наличие evidence и число в ответе. Примеры:

- «Сколько завершённых проверок по ипотеке в 2026 году?» → `5`;
- «Сколько завершённых проверок по вкладам в 2026 году?» → `2`;
- «Сколько открытых пунктов с просроченным сроком по ипотеке в 2026 году?» → `16`;
- готовый шаблон «топ-5 отклонений»;
- drill-down по `AUD-2026-MORTGAGE-02`;
- поиск по смыслу про оценку залога;
- отказ вне домена и отказ на изменение данных.

### Complex — несколько инструментов или длинный сценарий

- multi-tool: `get_act_items` + `search_acts` в одном ходе;
- проект раздела акта с `audit`/`citation` evidence;
- investigation с минимум двумя ACL-раундами;
- динамика пунктов по темам за 2025 и 2026 годы;
- повторные находки из актов.

### Chain — контекст диалога

В цепочке все реплики идут в одной нити `thread_id`. Проверяется, что
уточнение превращается в самостоятельный вопрос:

| Цепочка | Что проверяется |
|---|---|
| `chain_year_theme` | «А за 2025 год?» → «А по картам?»: год сохраняется, тема заменяется |
| `chain_open_items` | «А по картам?» → «А за 2025 год?»: тема сохраняется, год заменяется |
| `chain_drilldown_context` | код `AUD-2026-MORTGAGE-02` переносится в следующие вопросы |
| `chain_report_context` | «Сделай его короче» и «Добавь ссылку на пункт 5.1» остаются про тот же акт |
| `chain_ui_recovery` | после смены нити контекст восстанавливается из `client_history` |

Числа в цепочках подобраны разными (`5 → 8 → 7`, `40 → 35 → 16`,
`2 → 6 → 8`), чтобы правильный ответ нельзя было получить случайно,
не перенеся год или тему.

## Формат кейса

```json
{
  "id": "chain_year_theme",
  "tier": "chain",
  "title": "Уточнение года, затем темы",
  "auditor_id": "AUD-004",
  "turns": [
    {
      "query": "Сколько завершённых проверок по ипотеке в 2026 году?",
      "expected_route": "analytics",
      "expected_numbers": [5],
      "min_evidence": 1
    },
    {
      "query": "А за 2025 год?",
      "expected_route": "analytics",
      "expected_context": ["2025", "ипотек"],
      "expected_numbers": [8],
      "min_evidence": 1
    }
  ]
}
```

Поля реплики:

| Поле | Смысл |
|---|---|
| `expected_route` | ожидаемый маршрут основного графа |
| `expected_strategy` | `generated`, `script`, `drilldown`, `multi_tool` для Analytics |
| `expected_tools` | инструменты, которые должны быть использованы |
| `expected_evidence` | обязательные типы evidence (`sql_result`, `item`, `audit`, `citation`) |
| `min_evidence` | минимум записей evidence |
| `min_acl_rounds` | минимум раундов investigation |
| `expected_numbers` | самостоятельные числа в ответе |
| `must_include` / `must_not_include` | обязательные и запрещённые фрагменты ответа |
| `expected_context` | сущности, которые должны сохраниться из предыдущих реплик |
| `reset_thread` | начать новую нить и передать историю через `client_history` |

## Метрики

Эффективность:

- `latency_mean_sec`, `latency_p50_sec`, `latency_p95_sec`;
- `avg_tools_per_turn` — среднее число инструментов на реплику;
- `turns`, `cases`.

Качество:

- `route_accuracy` — совпадение маршрута;
- `success_rate` (SR) и `error_rate` (ER = 1 − SR);
- `case_success_rate` — доля кейсов, где успешны **все** реплики;
- `numeric_accuracy` — числа в ответе;
- `tool_accuracy` — ожидаемые инструменты;
- `strategy_accuracy` — выбранная стратегия Analytics;
- `evidence_coverage` — evidence для фактических ответов.

Контекст:

- `context_retention_rate` — сущность сохранилась в `resolved_query`
  **или** в ответе;
- `context_rewrite_rate` — сущность явно попала в `resolved_query`;
- `context_answer_rate` — сущность видна в ответе;
- `chain_context_retention_rate` — то же только по цепочкам.

`context_retention_rate` терпима к двум рабочим путям: rewrite-модель
переформулировала вопрос **или** подагент восстановил сущность из
`conversation_context`. `context_rewrite_rate` показывает, насколько хорошо
работает именно переформулировка.

## Запуск

```powershell
# структура набора без LLM и БД
.venv\Scripts\python.exe scripts\benchmark.py --dry-run

# только простые вопросы
.venv\Scripts\python.exe scripts\benchmark.py --tier simple

# только цепочки
.venv\Scripts\python.exe scripts\benchmark.py --tier chain

# один кейс
.venv\Scripts\python.exe scripts\benchmark.py --only chain_year_theme

# ограничить число кейсов
.venv\Scripts\python.exe scripts\benchmark.py --limit 3
```

Полный прогон требует `OPENAI_API_KEY`, построенный RAG-индекс и свободный
лимит провайдера. На free-тарифе NeuralDeep — 400 chat-запросов за 3 часа;
28 реплик расходуют лимит примерно на 7%.

## Как читать отчёт

В `reports/benchmark.md`:

1. **Итог** — общие метрики.
2. **По уровням** — сравнение `simple`, `complex`, `chain`.
3. **Кейсы** — успех по каждому кейсу.
4. **Цепочки** — видно `resolved_query` и отдельно отметки «В запросе» /
   «В ответе».
5. **Ошибки** — что именно не прошло.

Типичные выводы:

- высокий `success_rate` на `simple`, но низкий на `chain` → страдает
  перенос контекста, а не базовые инструменты;
- низкий `context_rewrite_rate` при высоком `context_retention_rate` →
  rewrite-модель не переформулирует, но подагенты спасают контекст;
- ошибки в `chain_ui_recovery` → `client_history` не доходит до
  `build_dialogue_context` или теряется при смене нити.

## Воспроизводимость

- seed данных 42;
- фиксированная дата среза `2026-11-21`;
- temperature 0;
- ожидаемые числа рассчитаны по baseline seed 42;
- для кейсов используется `AUD-004` без персональных предпочтений в
  `auditor_memory`, чтобы профиль не влиял на формат отчёта.

Если данные перегенерированы с другим seed, числа в `expected_numbers`
нужно пересчитать.
